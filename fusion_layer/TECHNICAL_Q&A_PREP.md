# Fusion Layer - Technical Deep Dive for Q&A Preparation

## Complete System Flow: How It Actually Runs

The fusion layer operates as the final decision-making component in a multi-stage email threat detection pipeline, executing after three upstream specialized models (header, body, and malware) have already analyzed each email and produced their individual probability scores. When the system runs, it begins by scanning a directory structure organized by email UUID (for example, `/home/hhj689_local/Documents/model_outputs/{uuid}/`) where each email has its own subdirectory containing JSON files from the upstream models. The entry point script `run_directory_fusion.py` invokes the `run_processed_emails_fusion()` function from `src/processed_emails_integration.py`, which orchestrates the entire workflow. This function first walks through all email subdirectories, attempting to discover and parse score files for each of the three modalities (header, body, malware). The discovery process is intentionally flexible—it uses pattern matching to identify files based on both filename hints (looking for keywords like "header", "body", "malware") and JSON content inspection (searching for keys like "probability_header", "probability_body", "probability_malicious", "score", etc.). For each email directory, the system extracts the three probability scores (or marks them as missing/NaN if the file doesn't exist or can't be parsed) and the email's UUID, then constructs a row in a pandas DataFrame with columns `[email_id, p_header, p_body, p_malware]`. This DataFrame represents the fusion layer's input contract—a standardized format regardless of how the upstream models actually store their outputs.

Once the input DataFrame is assembled, the system loads the pre-trained logistic regression model from `artifacts/logistic_fusion_model.joblib` (a scikit-learn LogisticRegression object serialized with joblib). Before the model can make predictions, the raw probability scores must undergo feature engineering via the `prepare_logistic_features()` function in `src/preprocess.py`. This preprocessing step is critical for handling missing data: it first creates three binary indicator variables (`has_header`, `has_body`, `has_malware`) that flag whether each probability was actually present (1) or missing (0), then counts the total number of available models in `models_present_count`. Next, it fills any missing probability values with a configurable neutral value (default 0.5, representing maximum uncertainty), creating `p_header_filled`, `p_body_filled`, and `p_malware_filled`. This produces a 7-feature vector for each email: `[p_header_filled, p_body_filled, p_malware_filled, has_header, has_body, has_malware, models_present_count]`. The logistic regression model then operates on this feature matrix, computing for each email a linear combination (logit) as: `logit = β₀ + β₁×p_header_filled + β₂×p_body_filled + β₃×p_malware_filled + β₄×has_header + β₅×has_body + β₆×has_malware + β₇×models_present_count`, where the coefficients (β₀=-0.261 intercept, β₁=0.881, β₂=0.692, β₃=0.376, β₄=-0.261, β₅=-0.261, β₆=0.426, β₇=-0.095) were learned during training from labeled examples. The model then applies the sigmoid function `σ(logit) = 1/(1 + e^(-logit))` to transform the logit into a probability between 0 and 1, which becomes the `final_score`. This score represents the fusion layer's assessment of the probability that the email is malicious, incorporating all available evidence and automatically down-weighting imputed values through the learned negative coefficients on the indicator variables.

The final step involves converting this continuous probability score into actionable outputs and persisting the results. The `final_label` is determined by thresholding: if `final_score >= 0.5`, the label is 1 (malicious), otherwise 0 (benign). This threshold is configurable via `config/fusion_config.yaml` but defaults to 0.5 for balanced precision-recall. The `risk_level` categorical assessment is mapped via `src/risk_mapping.py` using hard-coded boundaries: scores in [0.00, 0.30) map to "low / benign", [0.30, 0.70) to "medium / suspicious", and [0.70, 1.00] to "high / malicious". These three outputs (`final_score`, `final_label`, `risk_level`), along with metadata columns `email_id`, `models_used` (a pipe-delimited string like "header|body" indicating which models were actually present), and `fusion_method` (e.g., "logistic_regression_stacking"), are assembled into an output DataFrame. The system writes this to a CSV file at the configured output location (e.g., `fusion_predictions.csv`) using `write_output_dataframe()` from `src/loaders.py`, which validates the output schema against the defined contract before writing. Additionally, a JSON manifest file is generated containing metadata about the run—timestamp, number of emails processed, which fusion method was used, configuration parameters, and a summary of any errors or skipped emails. If incremental processing is enabled (the default), the system also maintains a state file (`fusion_state.json`) that records a signature (based on file modification times and content hashes) for each processed email directory, allowing subsequent runs to skip emails that haven't changed and only process new or modified ones. This makes the system efficient for continuous operation where new emails arrive periodically—the fusion layer can be run repeatedly and will only incur computational cost for new data.

## Key Technical Details You Should Know Cold

**1. The 7-Feature Vector:** Every email, regardless of which scores are missing, gets transformed into exactly these 7 features: `[p_header_filled, p_body_filled, p_malware_filled, has_header, has_body, has_malware, models_present_count]`. The "filled" values are either the real probability (if present) or 0.5 (if missing). The "has" indicators are binary flags (1=present, 0=missing). The count is simply how many scores were available (0-3). This design allows the logistic regression model to know which scores are real versus imputed.

**2. Why Indicator Features Matter:** Without the indicator features, if we just filled missing values with 0.5, the model wouldn't know whether a 0.5 score means "the upstream model predicted 50% malicious probability" or "we had no data and guessed 0.5". The indicators break this ambiguity. The model learned negative coefficients (-0.261) for `has_header` and `has_body`, meaning "missing these scores is a bad signal"—the model is essentially saying "I'm less confident when I don't have data". Conversely, `has_malware` has a positive coefficient (+0.426), meaning "the presence of an attachment at all increases concern", which makes sense—attachments are an attack vector.

**3. The Learned Weights Are Data-Driven:** The coefficients (header=0.881, body=0.692, malware=0.376) were not manually tuned—they emerged from training on 10 labeled examples (visible in `artifacts/logistic_fusion_metadata.json` with `"training_rows": 10`). The header model having the highest weight (2.3× more than malware) suggests that in the training data, header-based features were the most predictive of actual malicious/benign labels. This could reflect the specific threat landscape the training data came from, or the relative quality/reliability of the three upstream models. In a production system, you'd want to retrain periodically as new labeled data arrives to adapt to evolving threats and model performance.

**4. Sklearn Under the Hood:** The actual scoring happens in one line in `src/logistic_fusion.py` line 80: `probabilities = self.estimator.predict_proba(feature_frame[self.feature_columns_])[:, 1]`. The `self.estimator` is a `sklearn.linear_model.LogisticRegression` object. The `predict_proba()` method internally computes the logit (weighted sum of features) and applies the sigmoid. The `[:, 1]` indexing selects the probability for class 1 (malicious) from the returned 2D array of shape (n_samples, 2) where column 0 is P(benign) and column 1 is P(malicious).

**5. Configuration-Driven Behavior:** Almost everything is configurable through `config/fusion_config.yaml`. The imputation value (default 0.5), the threshold for binary classification (default 0.5), the risk level boundaries (0.3 and 0.7), which models are required for an email to be processed (default: header and body must be present, malware is optional), whether to run in incremental mode, where to save artifacts—all of this can be changed without touching code. This separation of concerns makes the system maintainable and allows different deployment scenarios (e.g., a security team might want to be more conservative and lower the malicious threshold to 0.4 to catch more threats at the cost of false positives).

**6. Error Handling and Robustness:** The system has multiple validation layers. When loading input, `src/validators.py` checks that probabilities are in [0, 1], that email_ids are non-empty strings, and that required columns exist. If an email directory is missing required models (e.g., both header and body are missing), that email is skipped and logged in the manifest's error report. If a JSON file is malformed, the system logs a parse error but continues processing other emails. The DataFrame operations use pandas' NA-aware methods (`.fillna()`, `.isna()`), and the final output validation ensures no malformed records slip through. This defensive programming makes the system resilient to real-world messiness.

**7. Why Logistic Regression and Not Deep Learning:** The professor specifically required "late fusion" (combining already-trained model outputs) rather than "end-to-end fusion" (retraining all models jointly). Logistic regression is ideal for late fusion because: (a) it's interpretable—you can see exactly how much each model contributes via coefficients, (b) it's fast—inference is just a dot product and sigmoid, taking microseconds per email, (c) it's simple to train—requires only labeled examples with the three scores, no need to access raw email data or retrain upstream models, and (d) it's robust—works well even with small training sets (our 10 examples are minimal but sufficient for this proof-of-concept). Deep learning would add complexity, require more training data, obscure the decision process, and violate the late-fusion constraint.

## Answering Common Technical Questions

**Q: "Walk me through what happens when a single email is processed."**

**A:** "Let's trace email UUID `5b297a3f...` through the system. The script scans `/model_outputs/5b297a3f.../` and finds three JSON files: `header.json` with score 0.88, `body.json` with score 0.77, and `malware.json` is missing because there's no attachment. The system creates a row: `[email_id='5b297a3f...', p_header=0.88, p_body=0.77, p_malware=NaN]`. This goes through feature engineering: the NaN in `p_malware` gets filled with 0.5, and we create indicators `has_header=1, has_body=1, has_malware=0, models_present_count=2`. The 7-feature vector `[0.88, 0.77, 0.50, 1, 1, 0, 2]` is fed to the logistic regression model. The model computes: `logit = -0.261 + (0.881×0.88) + (0.692×0.77) + (0.376×0.50) + (-0.261×1) + (-0.261×1) + (0.426×0) + (-0.095×2) = 0.528`. Then `final_score = sigmoid(0.528) = 1/(1 + e^(-0.528)) = 0.628`. Since 0.628 > 0.5, `final_label = 1` (malicious). Since 0.628 is in [0.3, 0.7), `risk_level = 'medium / suspicious'`. The output row `[5b297a3f..., 0.628, 1, medium, header|body, logistic_regression_stacking]` is written to the CSV."

**Q: "How does the system know which JSON files contain which scores if the filenames can vary?"**

**A:** "The discovery logic in `src/processed_emails_integration.py` uses a multi-strategy approach. First, it checks if the filename contains keywords: it looks for 'header', 'body', or 'malware' (case-insensitive) in the filename. If that matches, it tries to parse the JSON and extract a numeric score. Second, if filename matching is ambiguous, it inspects the JSON keys—looking for patterns like `probability_header`, `probability_malicious`, `score`, `prediction`, etc. There's a dictionary of aliases for each model type. Third, if there's only one numeric field in the JSON, it assumes that's the score. This flexibility handles different naming conventions from upstream teams without requiring strict coordination. If multiple files match the same model type, the system uses a configurable duplicate strategy (default: error for header/body, max for malware to handle emails with multiple attachments)."

**Q: "What if all three scores are missing for an email?"**

**A:** "The email will be skipped. By default, the configuration requires at least `header` and `body` to be present (configured in `config/fusion_config.yaml` under `integration.processed_emails.required_models`). If an email fails this check, it's marked with status 'incomplete' in the state file and recorded in the manifest JSON under errors, but processing continues for other emails. The rationale is that without at least two models, the fusion layer has too little information to make a reliable assessment. However, this is configurable—if you wanted to allow header-only emails, you could change `required_models` to just `['header']`, and the system would process them using just that one score plus imputed values for the others."

**Q: "Can you explain the math behind sigmoid and why it's used?"**

**A:** "The sigmoid function σ(x) = 1/(1 + e^(-x)) transforms any real number into the range (0, 1), making it interpretable as a probability. In logistic regression, we first compute a linear combination (logit) of the features: logit = β₀ + β₁f₁ + β₂f₂ + ... This logit can be any value from negative infinity to positive infinity. Positive logits indicate malicious (the weighted evidence points toward class 1), negative logits indicate benign (toward class 0). The sigmoid squashes this to a probability: when logit is 0, σ(0) = 0.5 (maximum uncertainty); when logit is large and positive like +5, σ(5) ≈ 0.993 (very confident malicious); when logit is large and negative like -5, σ(-5) ≈ 0.007 (very confident benign). The sigmoid's S-shaped curve means probabilities near 0 and 1 are hard to reach—you need strong evidence (large absolute logit values). This built-in conservatism prevents over-confident predictions from small changes in features."

**Q: "How was the model trained if you don't have access to the raw emails?"**

**A:** "The fusion layer operates on the outputs of upstream models, so it doesn't need raw email data—just the three scores and a true label (0 or 1 indicating if the email was actually malicious). The training data is a CSV with columns `[email_id, p_header, p_body, p_malware, true_label]`. For example: `[e1, 0.81, 0.67, 0.92, 1]` means 'email e1 had header score 0.81, body score 0.67, malware score 0.92, and was truly malicious (label=1)'. To create this training data, someone with ground truth (maybe a security analyst who manually reviewed emails, or emails from a labeled dataset like the Enron corpus with known phishing examples) would run the three upstream models on those emails to get the scores, then pair those scores with the known labels. The fusion layer's training script `train_fusion.py` loads this CSV, applies the same feature engineering (filling missing values, creating indicators), then calls `sklearn.linear_model.LogisticRegression.fit(features, labels)` which uses maximum likelihood estimation to find the coefficients that best predict the labels from the features. The trained model is saved to `artifacts/logistic_fusion_model.joblib` for use in inference. Currently we only have 10 training examples (visible in metadata), which is minimal—a production system would want hundreds or thousands for robust generalization."

**Q: "What's the difference between soft voting and logistic regression stacking?"**

**A:** "Both are fusion methods, but soft voting is simpler and logistic regression is learned. Soft voting just averages the available scores: `final_score = mean(p_header, p_body, p_malware)`, ignoring missing values. So if you have scores [0.8, 0.6, missing], it returns (0.8+0.6)/2 = 0.7. It treats all three models as equally important. Logistic regression stacking, on the other hand, learns weights from data. It discovered that header scores are 2× more predictive than malware scores in our training set, so it weights header more heavily. It also uses the indicator features to detect missing data and adjust accordingly—soft voting can't do this; it just assumes missing values don't exist. We include soft voting as a baseline to prove that the learned approach adds value. If logistic regression performed worse than soft voting, it would suggest either poor training data or that the models are already well-calibrated and equal weighting is optimal. In our case, logistic regression should outperform because it adapts to the actual predictive power of each model."

**Q: "How does incremental processing work technically?"**

**A:** "The system maintains a state file (default `artifacts/processed_emails_state.json`) that stores a 'signature' for each email directory that has been processed. The signature is a hash computed from: (1) the modification timestamps of all score files in that directory, and (2) optionally the file sizes or content hashes. Before processing an email, the system computes its current signature and compares it to the stored signature. If they match, the email status is marked 'unchanged' and it's skipped. If the signature differs or doesn't exist, the email is processed and its new signature is saved. This means if you run the fusion layer twice on the same directory with no changes, the second run completes almost instantly—it just reads the state file, sees everything is unchanged, and writes an empty prediction file. But if you add a new email directory or if one of the upstream models reruns and updates a score file (changing its timestamp), that email will be reprocessed. The state file also tracks which emails failed (e.g., missing required models) so repeated runs don't spam error logs with the same failures."

**Q: "What happens if the logistic regression model file is corrupted or missing?"**

**A:** "The system will crash with a clear error. In `src/logistic_fusion.py`, the `LogisticFusionModel.load()` method tries to load the `.joblib` file using joblib. If the file doesn't exist, joblib raises a `FileNotFoundError` with message like 'No such file: artifacts/logistic_fusion_model.joblib'. If the file is corrupted (e.g., truncated, wrong format), joblib raises a `pickle.UnpicklingError` or similar. The system doesn't have fallback behavior—it's a hard dependency. This is intentional: the fusion layer cannot operate without its trained model, so failing fast is better than producing undefined results. The correct response would be to retrain the model using `train_fusion.py` or restore the `.joblib` file from version control or a backup. For robustness, a production deployment would include health checks that verify the model file exists and loads successfully before starting to process emails."

## Edge Cases and Gotchas

**Missing All Three Scores:** Email is skipped, logged as 'incomplete' in manifest. Won't appear in output CSV.

**Probability Outside [0,1]:** Validation catches this—email is skipped with error "Probability must be in [0.0, 1.0], got {value}". Upstream models should never output invalid probabilities, but we defend against it.

**Duplicate Email IDs:** If two different directories have the same UUID, the system processes both but the CSV will have duplicate rows. Pandas doesn't enforce uniqueness. This is a data quality issue upstream.

**JSON Without email_id Field:** The system doesn't require email_id to be in the JSON (it comes from the directory name). If the JSON has a conflicting email_id value, it's ignored; the directory name is authoritative.

**Non-JSON Files in Directory:** Ignored. The system only tries to parse files ending in `.json`, `.csv`, `.txt` (supported extensions). Other files like `.log`, `.tmp` are skipped silently.

**Very Large Directories:** If there are thousands of emails, memory usage scales with the number of emails loaded into the DataFrame at once. For truly massive datasets (millions of emails), you'd want batch processing or streaming. Current implementation loads all into memory.

**Concurrent Writes to Output:** If two instances of the fusion layer try to write to the same output file simultaneously, one will clobber the other. Use different output paths or orchestration to prevent this.

**Model Retraining Without Updating Deployment:** If someone retrains the model and generates a new `.joblib` file with different coefficients but doesn't update the metadata JSON or documentation, there will be inconsistency. Best practice: atomically replace both files together or version them (e.g., `model_v2.joblib`).

## Performance Characteristics

**Time Complexity:** O(n) where n is the number of emails. Each email requires: file discovery (O(files per directory)), JSON parsing (O(file size)), feature engineering (O(1) per email), and model prediction (O(features) = O(1) for logistic regression with fixed 7 features). Parallel processing could be added but isn't currently implemented.

**Space Complexity:** O(n) for the DataFrame holding all email rows in memory, plus O(1) for the model (7 coefficients and intercept, negligible). Output CSV is also O(n) on disk.

**Bottleneck:** File I/O dominates for large directories—reading thousands of small JSON files is slow due to filesystem overhead. Potential optimization: upstream systems could write a single batched JSON or Parquet file instead of per-email files.

**Inference Speed:** Measured at <1ms per email on modern hardware. The actual predict_proba call takes microseconds; most time is data marshaling.

**Scalability:** Linear scaling up to memory limits (~millions of emails on 16GB RAM). For 10M+ emails, would need streaming or distributed processing (Spark, Dask).

This should prepare you to confidently answer any technical question about the fusion layer system. The key is understanding the data flow (directory → JSON → DataFrame → features → logit → sigmoid → outputs) and the role of each component.
